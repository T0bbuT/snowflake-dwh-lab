# ADR-0003: Goldビューのキーに決定的ハッシュを使用する

- ステータス: 採用
- 由来: 固有
- 決定日: 2026-06-09
- 記録日: 2026-09-23
- 事後記録: Yes

## 背景・課題

参照元のGoldはビューであり、顧客と商品のサロゲートキーを`ROW_NUMBER()`で生成している。行番号は並び順と対象行の集合に依存するため、行の追加・削除や並び順の変化によって、同じ顧客・商品に異なるキーが割り当てられる可能性がある。

本プロジェクトもGoldをビューとして提供するため、ビューを評価するたびにキーを計算する。履歴管理は行わないが、同じ自然キーからは同じGoldキーを得られることが望ましい。

## 決定事項

`DIM_CUSTOMERS.CUSTOMER_KEY`はCRMの`CST_ID`、`DIM_PRODUCTS.PRODUCT_KEY`はCRMの`PRD_ID`を`MD5`へ渡して生成する。FactはGoldディメンションへ結合し、同じキーを参照する。

このキーはSnowflakeテーブルで採番・永続化するキーではなく、自然キーから決定的に導出する分析用のキーとして扱う。

## 検討した選択肢

### ROW_NUMBERによる連番

参照元と同じ方式だが、行の追加・削除や並び順の変化によって既存エンティティのキーが変わり得るため採用しない。

## 影響

- 同じ自然キーに対して、Goldビューを再評価しても同じキーを生成できる。
- 顧客キーと商品キーを同じ32文字の形式で提供できる。
- MD5には理論上の衝突可能性がある。
- ソース側で自然キーが変更された場合は、同じエンティティでも別のGoldキーになる。
- SCDを導入する場合、この方式だけでは同一エンティティの複数バージョンを識別できない。

## 見直し条件

- 履歴管理またはSCDを導入する場合
- Goldを物理テーブルとして保持する場合
- 衝突耐性に関する要件が追加された場合
- 複数ソースで自然キーの名前空間が重複する場合
