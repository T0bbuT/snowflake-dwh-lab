# ADR-0008: 対象DB名を実行時に渡し、検証DBをリポジトリのSQLから構築する

- ステータス: 採用
- 由来: 固有
- 決定日: 2026-10-26
- 記録日: 2026-10-26
- 事後記録: No

## 背景・課題

SQL内のオブジェクト参照は `DATA_WAREHOUSE.<スキーマ>.<オブジェクト>` の完全修飾名で固定されていた。DDL・ロードプロシージャの本体・Goldビュー・品質チェック・ログ設定のほぼすべてが該当する。

AGENTS.mdでは実機検証に専用の検証DBを使うことにしている。しかし、これまでの検証（[2026-09-13](../validation-2026-09-13.md)、[2026-09-21](../validation-2026-09-21.md)、[2026-10-04](../validation-2026-10-04.md)）では、毎回SQL内のDB名を手作業で置き換えていた。さらにログ出力先の設定は、`ALTER ACCOUNT` から `ALTER DATABASE` へ書き換えて実行していた。この方式には次の問題がある。

- 置き換え漏れがあると、検証のつもりで既存DBのテーブルを `TRUNCATE` する。
- 検証で実行したSQLとリポジトリのSQLが一致せず、検証結果がリポジトリのSQLを保証しない。
- アカウント全体のログ出力先は1つしか設定できないため、検証DBのログを分離するには手順の書き換えが必要になる。

## 決定事項

- SQL内のDB名はSnowflake CLIのテンプレート変数 `<% db %>` で記述する。既存DB・検証DBとも同じファイルを使い、実行時に `snow sql -D db=<DB名>` で指定する。
- ログ出力先はDB単位（`ALTER DATABASE <% db %> SET EVENT_TABLE`）で設定する。各DBのプロシージャのログは同じDBのEvent Tableへ出力し、アカウント全体の設定は変更しない。
- 検証DBは変更ごとにリポジトリのSQLから構築し、検証後に削除する。

Snowflake CLI 3.26.0で次を確認した。

- `$$` で囲んだプロシージャ本体の中も置き換わる。
- `!source` で読み込んだファイルにも変数が引き継がれる。
- `-D db=...` を省略すると `'db' is undefined` で停止し、SQLは実行されない。

## 検討した選択肢

### 既存DBのゼロコピークローンを検証DBにする

構築の手間は少ないが、クローンしたプロシージャ・ビューは既存DBの完全修飾名を参照したままになる。そのため、クローン側で `LOAD_SILVER()` を呼ぶと既存DBのテーブルを `TRUNCATE` する。また、クローンは既存DBの現状を再現するもので、リポジトリのSQLで構築できるかは確認できない。CSVはリポジトリにあり、構築からロードまでの再現は数分で済むため採用しない。既存DBのデータで事象を調査する用途に限る。

### 完全修飾名をやめ、カレントDBで名前を解決する

テンプレート変数が不要になるが、プロシージャ・ビュー内の名前がどのDBに解決されるかが実行時のコンテキストに依存し、読み手から分かりにくい。参照先を明示できるテンプレート変数を選ぶ。

## 影響

- 検証DBと既存DBで同じSQLを実行でき、検証結果がリポジトリのSQLを直接保証する。
- 変数を省略した実行はSQLの実行前に失敗するため、意図しないDBへの実行を防げる。対象DB名の指定誤りは防げないため、実行前にDB名を確認する。
- すべての `snow sql -f` に `-D db=...` が必要になる。
- テンプレート変数を含むファイルは、SnowsightやVS Codeからそのままでは実行できない。
- ログ出力先の設定に必要なロールは引き続き `ACCOUNTADMIN` である。
- 既存DBにDB単位の出力先を設定するまでは、既存DBのログはアカウント単位の設定で記録される。

## 見直し条件

- 環境ごとにロール・ウェアハウスも切り替える必要が生じた場合
- CI・スケジューラーから構築・ロードを自動実行する場合
- Snowsightから構築・検証を実行する必要が生じた場合
