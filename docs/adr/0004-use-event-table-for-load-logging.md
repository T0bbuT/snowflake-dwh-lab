# ADR-0004: ロードログをEvent Tableへ記録する

- ステータス: 採用
- 由来: 固有
- 決定日: 2026-09-13
- 記録日: 2026-09-23
- 事後記録: Yes

## 背景・課題

当初のロードプロシージャは、処理状況を一つの文字列へ連結して戻り値として返していた。この方式では、その場で結果を確認できる一方、過去の実行履歴、テーブル別の処理件数、処理時間、エラーを後から横断的に調査しにくい。

Snowflakeはストアドプロシージャからログを出力し、Event Tableへ保存する仕組みを提供している。

## 決定事項

BronzeとSilverのロードプロシージャは、`SYSTEM$LOG_INFO`と`SYSTEM$LOG_ERROR`で次の情報を記録する。

- バッチと各テーブルの処理開始
- テーブルごとのロード件数と処理時間
- バッチ全体の処理時間
- 例外発生時のメッセージとエラーコード

プロシージャの戻り値は、呼び出し元が後続処理へ進めるか判断できるよう、成功時は`SUCCESS`、失敗時は`ERROR: ...`とする。

## 検討した選択肢

### 戻り値にログ全体を含める

永続的な履歴として検索しにくいため、成功・失敗の通知だけに限定する。

## 影響

- Snowflake上で過去のロードログとエラーを検索できる。
- ロードの戻り値と詳細ログの役割が分離される。
- Event Tableへの反映には遅延が生じる場合がある。
- Event Tableの出力先設定はアカウント全体に影響し、`ACCOUNTADMIN`が必要になる。
- 厳密なバッチ単位の監査、即時参照、ログ保持期間の管理が必要になれば、専用の監査テーブルが必要になる可能性がある。

## 見直し条件

- バッチIDを用いた実行単位の追跡が必要になった場合
- ログの即時参照または厳密な監査証跡が必要になった場合
- 複数のプロジェクトが同じアカウントのEvent Table設定を共有する場合
