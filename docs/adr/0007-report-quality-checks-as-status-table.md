# ADR-0007: 品質チェックを合否付きの一覧で出力する

- ステータス: 採用
- 由来: 固有
- 決定日: 2026-10-04
- 記録日: 2026-10-04
- 事後記録: No

## 背景・課題

元教材の品質チェックは、チェックごとに独立したクエリで、「結果なし」を期待するクエリと、`SELECT DISTINCT` で値の分布を表示するクエリが混在している。本プロジェクトのSilverチェックは18個の結果を返し、実行者は次の判断を毎回行う必要があった。

- どのクエリが「0件であるべき」もので、どれが「分布を見る」ものか
- 分布の一覧に想定外の値が混ざっていないか
- 行が返った「確認対象」（古い生年月日、売上を算出できない明細）が、不具合か仕様どおりか

分布チェックには合否がなく、想定外の値が混ざっても実行者が気づかなければ通過する。また、CLIの出力から合否を機械的に判定できなかった。

## 決定事項

Silver・Goldの品質チェックは、それぞれ1つのクエリで、チェックごとに次の1行を返す。

| 列 | 内容 |
| --- | --- |
| `check_id` / `check_name` | チェックの識別子と内容 |
| `severity` | `ERROR`（不正値。0件であるべき）または `WARN`（確認対象。行があっても不正とは限らない） |
| `failed_rows` | 条件に該当した行数 |
| `status` | `PASS`（0件）、`FAIL`（`ERROR` で1件以上）、`WARN`（`WARN` で1件以上） |
| `examples` | 該当した値またはキーの例（重複を除き最大5件） |

分布の確認は、許可する値の一覧以外を数えるチェックへ置き換える。一覧外の値が不具合とは限らないもの（国）は `WARN` とする。実行者は `FAIL` がないことを確認し、`WARN` は件数と例を見て判断する。

## 検討した選択肢

### ロードプロシージャ内でチェックを実行する

チェックの実行漏れを防げるが、ロードと品質確認の責務が混ざる。まず出力形式を統一し、必要になった時点で検討する。

### Snowflakeのデータメトリック関数（DMF）を使う

Snowflakeの機能で品質を継続監視できるが、利用可能なエディションや運用コストを確認していない。本プロジェクトの規模では、SQLファイルで十分と判断した。

## 影響

- 品質確認の判断が `status` 列に集約され、手順書の確認内容が単純になる。
- `examples` から調査対象を特定でき、多くの場合は追加のクエリが不要になる。
- 分類値に許可されていない値が混入した場合、`FAIL` として検出される。
- 分類値の一覧を変更した場合は、LOAD_SILVERの変換とチェックの許可値を合わせて更新する必要がある。
- 詳細な行の確認には、チェックの条件を使って別途クエリを書く必要がある。

## 見直し条件

- チェックの実行漏れが問題になった場合
- CI・スケジューラーなどから品質チェックを自動実行する場合
- チェック数が増え、1つのクエリでの管理が難しくなった場合
