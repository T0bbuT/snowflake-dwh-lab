## 検証範囲

- 既存の `my_connection` で接続テストに成功。認証鍵の新規作成やGit Workspaceの新規設定は対象外です。
- 専用DB `DATA_WAREHOUSE_E2E_20260912_01` を新規作成。SQLは作業時点のローカルファイルを使い、DB名を置き換えて実行しました。
- Event Table設定だけは、既存アカウントに影響しないよう `ALTER ACCOUNT SET EVENT_TABLE` を検証DBへの `ALTER DATABASE ... SET EVENT_TABLE` に置き換えました。したがって、アカウント全体の出力先変更は今回の実行対象外です。DB単位の設定は[Snowflake公式ドキュメント](https://docs.snowflake.com/en/developer-guide/logging-tracing/event-table-setting-up)に基づきます。
- 6つのCSVは、公開リポジトリの同じファイルとSHA-256が一致することを確認して使用しました。
- 既存の `DATA_WAREHOUSE` のデータ・定義、およびアカウントのEvent Table設定は変更していません。
- 検証終了後に専用DBを削除し、DBが存在しないこととアカウントのEvent Table設定が元のままであることを確認しました。

## 残る確認事項

検証時点の `quality_checks_silver.sql` の生年月日チェックは1926-01-01より前の値を抽出していました。一方、`LOAD_SILVER()` は未来の日付だけをNULLにし、古い日付は保持します。当時のチェックSQLのコメントにも、この下限はプロシージャで制限していないことが記載されていました。

今回の19件は検証当時の仕様に対応する確認事項です。この実機検証ではデータの補正やチェック基準の変更は行いませんでした。「ロードできること」と「全データの品質に問題がないこと」は別に評価してください。

その後、生年月日の確認基準を「実行日から120年前より古い日付」に変更しました（120年前の同日は対象外）。これは調査の目安であり、年齢だけを理由とするNULL化・削除は行いません。未来の日付をNULLにする変換処理は維持しています。上記の19件は旧基準での実績であり、新基準の検出件数ではありません。

検証は同一CSVの再ロードまでで、新しいデータ・異常ファイル・障害時の復旧は対象外です。再ロード前後では件数と既存品質チェックを照合しており、全行の値の完全一致は検証していません。
